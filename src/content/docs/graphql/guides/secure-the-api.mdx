Out of the box the API runs wide open, and there's no authentication code in it at all. That's lovely on a laptop and less lovely in production, so here's how to close the door.

## Turn it on

<Steps>

1. Create the solution with `--auth`, and tell it who issues tokens and who they're for:

   ```bash
   dotnet new cleangraphqlapi --name WorksOnMyMachine.Movies \
     --auth --authority https://login.example.com --audience https://movies.example.com
   ```

   `--authority` is required with `--auth`, so `dotnet new` stops and says so if it's missing. To point each environment at its own server, override the settings in `appsettings.json` or with environment variables:

   ```bash
   Authentication__Authority=https://login.example.com
   Authentication__Audience=https://movies.example.com
   ```

2. Get a token from the authority for that audience, and send it.

   ```bash
   curl -X POST "http://localhost:5032/graphql" -H "Authorization: Bearer eyJhbGciOi..." \
     -H "Content-Type: application/json" -d '{"query":"{ movies { totalCount } }"}'
   ```

   In Nitro, open the connection settings and add the token under **Authentication**.

</Steps>

## Add it to a solution you already have

Created the solution without `--auth`? The code isn't hiding behind a setting, it isn't there at all, so it goes in by hand. The quickest way to see every line is to let the template show you. Create a second solution with the same name and `--auth` next to yours, then compare the two:

```bash
dotnet new cleangraphqlapi --name WorksOnMyMachine.Movies --output ../with-auth \
  --auth --authority https://login.example.com --audience https://movies.example.com
git diff --no-index src ../with-auth/src
git diff --no-index tests ../with-auth/tests
```

Copy across what's new: the `Microsoft.AspNetCore.Authentication.JwtBearer` package reference, the `Authentication` folder and its section in `appsettings.json`, the authentication regions in startup, `[Authorize]` on the queries and mutations, the Hot Chocolate authorization package, the `ApplyPolicy` enum in the schema snapshot, and the authentication tests, so coverage stays where it was. The `optional-token-auth` skill in `.agents/skills` walks your coding agent through the same steps.

## What changes

- The protected fields answer with an error instead of data when the token is missing, from the wrong issuer or for the wrong audience. The HTTP status stays `200`, because that's how GraphQL does it.

  ```json
  { "errors": [ { "message": "The current user is not authorized to access this resource.", "extensions": { "code": "AUTH_NOT_AUTHENTICATED" } } ] }
  ```

- The `version` query needs one too. The schema, Nitro, `/health/live` and `/health/ready` stay open, so load balancers and curious humans can still check the lights are on.
- Tokens are validated against the authority's published keys, so there's no secret to store and nothing to rotate on your side.

## How it works

`AuthenticationSettings` reads the `Authentication` section, and the API registers the JWT bearer handler, the normal authorization services and Hot Chocolate's authorization. Every movie, author and review query, every mutation and the `version` query carry `[Authorize]`. An empty authority still lets every request through, which is how the tests run, so make sure every environment you deploy to sets one.

<Aside type="note" title="All or nothing">
  With `--auth`, every protected field declares it, so there's never a moment where a field was forgotten. Without it, there's no half-built gate left open by mistake. There's just no gate.
</Aside>

## Beyond a bearer token

Scopes, roles and per-field policies are a short step from here: add policies to `AddAuthorization` and ask for them with `[Authorize(Policy = "policy")]`. Which claims to check depends entirely on your identity provider, so the template stops at the door and lets you decide who gets past it.
